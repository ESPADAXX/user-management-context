## Context
REQ-002 asks for 8-hour tokens, REQ-003 for role changes applied on the next request, and REQ-005 for revoking every token of a deactivated user.

## Decision
- Access token: JWT signed with HS256, `sub` = user id, `tv` = the user's token version, expires in 8 hours.
- On every request the API loads the user from the database, so the current role and status always apply (REQ-003).
- Deactivating a user increments `token_version`; a token whose `tv` differs is refused with 401 (REQ-005).
- Passwords are hashed with bcrypt (cost 10).
- Failed sign-ins are stored per email; 5 within 15 minutes lock the email for 15 minutes (REQ-002 v2).

## Alternatives rejected
- Server sessions with cookies: needs CSRF protection and sticky storage for little gain here.
- OAuth / OpenID Connect provider: out of scope for this release; can replace sign-in later without changing roles.

## Consequences
- One database read per request; acceptable for the quality targets.
- `JWT_SECRET` must be set in production.
